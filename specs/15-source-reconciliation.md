# Spec 15 — Source Reconciliation and Handoff

## Purpose and status

This register compares the proposed behavior in specs 00-14 with executable evidence in the current repository. It is part of the specification until each open item is resolved. An implementation agent MUST NOT infer a resolution from the old source or treat an `AGENT` proposal as approved behavior.

Status labels:

- `SOURCE` — directly observed in the current source or executable configuration.
- `AGENT` — a recommended resolution that has not been approved by the user.
- `OPEN` — a decision whose resolution can change consumer-visible, security, persistence, or operational behavior.
- `RESOLVED` — a decision explicitly approved and reflected in the normative specs.

The clean-room implementation handoff is **FROZEN** for behavioral and technical requirements as `specs/00-15 v1.2`. The legacy `SOURCE` notes below are carried forward from the prior handoff document and were not independently inspected or used to shape this clean-room brief. Package/repository metadata inputs listed in Spec 14 remain prerequisites for final package-manifest and release-workflow wiring, but do not block local source implementation.

## Requirement Traceability

IDs are stable section-group identifiers. `VA-00-OVERVIEW`, `VA-00-ARCH`, `VA-00-SCENARIOS`, and `VA-00-REQUIREMENTS` refer to the corresponding named sections in [00-overview](00-overview.md). For Specs 01-14, `VA-<spec-number>-S<step-number>` identifies all material requirements in that numbered Step section. `VA-15-HANDOFF` identifies requirements in this register. Provenance for all IDs is `USER: approved clean-room specification`; decisions SR-01 through SR-13 have explicit user approval. IDs group requirements by section, not by individual sentence.

## Observable Acceptance Criteria

- `VA-AC-01`: Public exports, declarations, ESM package shape, peer dependency boundaries, and consumer imports agree with Specs 13-14.
- `VA-AC-02`: First provider render synchronously reflects persisted user state; SSR/non-browser rendering remains unauthenticated and starts no OIDC work.
- `VA-AC-03`: Sign-in, callback, return-URL restoration, timeout, storage failure, and URL cleanup match Specs 02-05 and 10, including malformed and cross-origin return URLs.
- `VA-AC-04`: Automatic, manual, and on-demand renewal; expiry; and cross-tab sign-out races match Specs 06-08.
- `VA-AC-05`: Identity/role accessors, role helpers, error state, and recovery transitions match Specs 09 and 11.
- `VA-AC-06`: Configuration identity, custom factory, client-cache lifetime, and provider remount behavior match Specs 01, 03, and 12.
- `VA-AC-07`: Artifact contents, tooling, verification, CI, audit, and provenance match Spec 14. Release metadata must be supplied before package/release wiring is finalized.

Acceptance evidence MUST verify observable behavior without source-layout or algorithm parity with a previous implementation. This specification update does not authorize adding or running tests.

## Historical Clean-room Handoff Gate (Superseded)

The following pre-resolution checklist is retained for historical traceability and is superseded by the approved resolutions above:

1. Resolve every `OPEN` item with an explicit user decision, or remove the decision only when its effect on observable behavior is demonstrably immaterial.
2. Update every affected normative spec and mark the matching register entry `RESOLVED`, including the decision's provenance.
3. Give each material requirement a stable identifier and source; mark agent recommendations and assumptions as unapproved until decided.
4. Ensure acceptance evidence covers successful and failed flows, state transitions, storage effects, navigation, SSR/non-browser behavior, cross-tab behavior, and package exports without requiring the replacement to copy private implementation structure.
5. Freeze a named revision of the specs as the sole implementation brief. The implementation agent MUST NOT inspect the old source, its diffs, screenshots, or implementation-specific documentation unless the user explicitly reopens that evidence.
